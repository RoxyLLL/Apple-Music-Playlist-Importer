# 实施计划（交 Antigravity）

## 1. 先固定契约与基线

- 保存 R1 至 R5 的失败用例，记录现有全量测试数量与结果；检查工作区用户改动。
- 为名称比较增加内部结构化表示：原文、规范化主名、官方/来源别名、转写变体、版本标签、provenance；歌手另区分 primary、featured、角色/CV、可用的 Apple artist ID。
- 不改变公开 `Track`/`SongMatchResult` 中原始显示字段的含义；新增字段向前兼容，缓存历史 JSON 可解析。

## 2. 修复名称解析与候选召回

- 在 `client.py:_parse_song_item` 保留完整 `artistName`。优先用 Apple 结构化 artists relationship/ID 确定多艺人；无结构化证据时，对逗号谨慎处理，不拆坏带逗号的单个艺名。
- 在 `cleaner.py` 将主艺人、客串和角色信息显式拆开，校验 `feat./ft./with/CV`、括号艺名、符号名称、纯汉字和中日同形字。清洗仅用于比较，原文保留。
- 在 `QueryContext/QueryPlanner` 引入来源译名和别名。对每个可查询变体标注来源、可信度、storefront/locale/cost；对同一含义查询稳定去重。
- 调整 `engine.py` 调度：原文和有来源的译名优先，跨文字候选选取有限组合；给日区发现留可执行额度，且不要让弱候选阻断后续探索。所有请求仍经过同一个总预算、限流和诊断记录。

## 3. 重构评分安全边界

- `scorer.py` 的 ISRC 路径先计算真实歌名/主艺人/版本分，再判断是否足够自动采纳。保留强 ISRC 依据，但对缺失和冲突元数据降级，绝不伪造字段满分。
- 主艺人、客串匹配分开计算；客串命中只是支持证据。不同 Apple artist ID 可作为冲突参考，但 relationship 缺失时保持未知，不自行推断为相同或不同。
- 把原文一致、明确译名、Apple 等价、ISRC 与机器转写分开记证据族。专辑/时长只能佐证，不能替代歌名和主艺人身份；避免同一信号在多字段重复加分。
- 统一分数归一化与缺失值处理，硬冲突先于阈值决策。当前 `score` 可继续用于排序和界面“匹配分”，阈值必须经困难负例与真实样本校验。
- 检查二号候选“同歌变体”豁免分差的条件：应同时考虑主艺人身份、版本、ISRC/等价关系，不得仅靠相似歌名和艺人模糊度。

## 4. 状态、缓存、界面

- 区分目标区确定无版权、检索未完成和仅发现弱日区候选；错误请求不得生成肯定的“未上架”结论。
- 将规则版本和查询策略版本升级；历史 `auto_accept` 读取时重评，`user_confirmed` 严格按原来源身份与目标区保留。
- 只在必要时调整 Web API/界面。先检查 `app.py` 与 `index.html` 的现有未提交改动；继续让 `review` 默认不选，并用“匹配分”而非未经校准的概率描述数值。

## 5. 交付

- 执行专项用例、全量回归、编译与 `git diff --check`，附上确切数量和结果。
- 使用只读、有来源的 Apple Catalog 响应或 ID 建立独立评估集，按日文/罗马字/译名/同形汉字/合作艺人/版本分桶；输出基线与新规则的 Recall@20、自动采纳误判、复核率、请求数/P95。若无法在线评估，只能声明功能测试通过、真实召回率未知。
- 写 `RESULT.md`：文件变更、每项 R1-R5 的前后结果、测试证据、风险；不提交、推送或发布，交 Codex 验收。
