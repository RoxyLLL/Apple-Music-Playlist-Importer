# 多语言歌曲漏召回修复规范

## 现象与已复现原因

截图源曲为 `One Last Kiss (最后一吻)` — `宇多田光 (宇多田ヒカル)`；手动搜索展示了 `One Last Kiss` — `Utada`，自动匹配却未选出歌曲。

当前 `QueryPlanner.plan_phases()` 对有歌手的歌曲只产生歌名＋歌手及别名组合，不保证执行歌名独立检索。Phase A 的别名来自集合，顺序不稳定；Phase A/B 共用约 5 次额度，后备检索容易被挤掉。使用截图的源/候选元数据直接调用 `TrackScorer` 时，标题相似度约 0.98、艺人相似度 0.15、综合分约 0.191，判为 `no_match`。

`Utada` 是这位艺人正式使用过的名字，见 [Sony Music 官方作品页](https://www.sonymusic.co.jp/Music/Info/utadahikaru/en/music/)的 “Works under the name of Utada”。此来源用于核实艺人别名；不得把此歌曲 ID、歌名或人工选定结果写入命中缓存池。

## 目标行为

1. 当严格查询尚未找到可自动采纳的候选时，为有辨识度的核心歌名保留一次目标区歌名独立查询额度；包含括号译名、跨脚本歌手名的曲目同样受益。查询要去重、顺序稳定，总预算仍不超过现有 8 次。标题过短或过于泛化时按现有严格评分保护，不能仅凭同名自动采纳。
2. 将经官方核实的 `Utada` 纳入 `宇多田光 / 宇多田ヒカル / Hikaru Utada` 的艺人身份组，并让歌手别名查询顺序确定。艺人同一性只给经过核实的完整别名；不能把任意姓氏、子串或仅同标题视为歌手匹配。
3. 保留现有标题、版本、艺人、ISRC、时长、冲突和分差保护。`One Last Kiss` — `Utada` 应在完整身份佐证后成为有效候选；同名翻唱、不同版本及不同歌手不得因标题回退而误采纳。若证据仍不足，返回 `review` 并显示候选；不可给无关歌曲虚高分。
4. 查询策略升级后，旧算法产生的 `no_match`（包括保存了低分候选的记录）必须重新检索，不能只对旧候选重评分后再次缓存为 `no_match`。旧 `review` 如可能被新查询改善，也应允许重新检索。`user_confirmed` 严格保留。无候选旧缓存和次级索引走同样规则。版本管理同时覆盖查询策略和艺人别名变更。
5. 失败语义不变：网络错误、授权失效、频控、目标区确实不可用都不能伪装成可靠 `no_match`。输出诊断中的实际查询词、阶段和结果，方便区分“未检索到”与“检索到但评分拒绝”。

## 验收边界

本次须修通自动检索和评分的整条链路，覆盖截图样例及通用负例；不得以单曲人工缓存、屏蔽评分保护、无限追加查询或提高所有候选分数作为修复。离线模拟不能证明线上曲库的实际召回率；若可连接真实 Apple Music，记录目标地区和匿名化诊断，不记录令牌。
