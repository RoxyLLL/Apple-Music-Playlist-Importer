# 日语罗马字漏判与同艺人异歌虚高分：V5 修订方案

流程：Codex 提供方案；Antigravity 编写代码、测试和 RESULT.md；Codex 独立验收。本次仅创建方案。无需提交、发布、打包或操作真实账号。

## 目标

- 正例：`好きだから。（因为我喜欢你。）` / `『ユイカ』` 对 `Sukidakara` / `Yuika`。正确识别核心标题的完整罗马字对应，不能靠时长兜底得到中等分。
- 反例：`sweets parade` / `花泽香菜 (はなざわ かな)` 对 `magical mode` / `花泽香菜`。同艺人、相近时长、Single 标签均不能证明同一首歌，不得默认选中。
- 覆盖同类歌曲，不添加这两首的缓存特判，不全局降低自动采纳门槛。

## 已核实的问题

1. `scorer.py::_calculate_title_similarity_cached` 的日语分支分别获取两侧转写变体。纯拉丁字母侧返回空列表，双层循环无法比较。因此生成器已输出 `sukidakara`，评分仍未命中。艺人评分已有非日语侧原文回退，标题评分没有。
2. `scorer.py::score` 的 `Strict Album Track Fingerprint Fallback`：艺人一致、候选专辑包含 Single/EP、时长误差不超过 2.5 秒，就把低歌名分覆写成 0.60，绕开低歌名保护。Single 标签不是同专辑证据，同艺人相同时长也不是歌曲身份。
3. 评分与证据来源分别计算。证据对原始全标题做转写，括号中文译名可能使输出为空；“没有直接匹配”还会被推断成“转写匹配”，即使实际没有命中转写。
4. `engine.py::_evaluate_and_aggregate` 的重试结果有 `no_match -> review` 放宽路径；有候选时把非自动结果的 `search_status` 都写成 `review`。评分修复后不能让引擎恢复明确拒绝的候选。
5. 历史 `stale-review-cache` 用例用了 `sweets paper`，此次截图是 `sweets parade`。新增精确截图用例，并保留旧例。

Codex 本次只用内存模型与模拟元数据调用评分函数，未读取生产缓存或真实凭证：

| 输入 | 当前 title_score | 当前总分/决策 |
| --- | --- | --- |
| 好きだから。（带中文括号）→ Sukidakara，艺人对应，无时长 | 0.15 | 0.150 / no_match |
| 同上，两侧模拟时长均 240000ms，候选 Single | 被覆写为 0.60 | 0.778 / review |
| sweets parade → magical mode，同艺人，无时长 | 0.24 | 0.166 / no_match |
| 同上，两侧模拟时长均 240000ms，候选 Single | 被覆写为 0.60 | 0.778 / review，证据甚至标为 strong |

截图缺少原始时长、专辑和缓存版本，未复现截图精确的 72 分；以上实验已证明通用漏判和虚高机制。Antigravity 可用脱敏诊断确认实际触发路径。

## 实施要求

### A. 标题分与证据使用同一个比较结果

在现有 cleaner/scorer 内提取内部标题比较结果（可用 dataclass），返回真实相似度、命中的双方变体、匹配方法和歧义。保持对外 `calculate_title_similarity` 等接口兼容，评分与 evidence 消费同一结果，避免重复推断。

- 分别比较核心标题、来源提供的译名/别名和候选标题变体。括号版本信息仍进入版本校验，不得丢失 Live、Remix、伴奏等冲突。
- 日语侧转写清理后的完整标题变体；拉丁字母侧保留规范化原文作为比较值。不要为全局生成器塞入任意原文来假装成功转写。
- `Sukidakara`、`Suki Dakara`、大小写与标点差异应与日文核心的完整罗马字相等。要求非空且完整；禁止空串相等、仅片段对应或默默丢掉未识别汉字。
- 完整且确定的转写对应可给予标题分至少 0.95。模糊拼写、推测的汉字多读音、外来词近似对应保留弱证据，不全部升级为确定身份。
- 艺人记录实际命中路径，覆盖书名号包装、假名、罗马字、可靠别名、主艺人与客串区别。`『ユイカ』 -> Yuika` 走通用处理。
- 未命中转写不能标为 `romanizer_derived`。matched_fields、真实分项和诊断方法必须一致。

### B. 歌曲身份不能由辅助元数据代替

- 删除“低歌名分直接改成 0.60”的行为，保留真实标题分。Single/EP 标签不得充当来源与候选的专辑一致证据，也不要用裸子串 `ep` 判断 EP。
- 两侧可直接比较、标题明确不同且没有可靠别名/身份映射时，记录 `title_mismatch`。同艺人、同专辑、同秒数不能覆盖冲突；ISRC 与可靠映射仍走已有核验规则，不伪造标题分。
- 跨文字体系但别名未核实时记录 `title_unverified`，不能武断宣称异歌，也不能仅凭辅助信息标为 strong 或默认选中。
- 明确异歌建议总分上限 0.39，决策必须 no_match。可按扩展矩阵校准具体上限，但不能超过人工推荐门槛、被默认选中或经重试恢复为 review。
- 时长与真实专辑一致只作佐证。重复艺人、重复转写器、重复查询和 Single 标签不算新的独立身份依据。缺失时长/专辑不编造中性分，也不是正例获得高分的必要条件。
- 相同 ISRC 但明显标题/主艺人/版本冲突继续阻止自动采纳，兼容已有 ISRC 冲突测试。

### C. 高分与自动采纳分开

- 完整标题转写对应、主艺人一致、无版本冲突时，即使没有专辑/时长也应得到至少 0.90 的匹配分。正例不能因缺少元数据被压到 72 分。
- 匹配分不是概率。保持当前自动采纳阈值与独立证据保护：标题和艺人都只依赖同一转写器时，可以高分 review，理由应是“标题/艺人转写吻合，身份待核验”，不能说歌名分低。
- 有可靠艺人身份依据或可靠目录映射，且满足标题、版本、分差等要求时，可 auto_accept。artist ID 单独不证明歌曲身份；discovery_path 字符串单独不证明映射成功。
- 常规核心标题一致的歌曲继续正常匹配，同名异艺人、客串倒置、短歌名、多读音、不同版本保持保护。

### D. 引擎、页面与缓存一致

- 正常检索、ISRC、JP 映射、重试、缓存重评共享拒绝规则。明确 title_mismatch 不能被“放宽推荐”重设为 review。
- 冲突候选不得压过无冲突的正确候选；全部不合格时 selected_candidate=None。诊断/手动搜索可查看候选，但不能自动勾选或同步。
- 全部候选拒绝时，search_status、decision 与页面一致显示“未找到可信匹配/候选不符”。当前通用“未收录”不能让用户误以为已证明 Apple Music 未收录。
- 诊断给出命中的双方变体、转写方法、真实分项、冲突与拒绝原因。同分不同决策要能解释。
- 升级 MATCH_RULE_VERSION，以及实际改变的转写/查询/别名版本，不机械升级所有版本。旧算法缓存重评或再搜索，不能继续展示旧 72 分。人工 user_confirmed 按现有约定保留。
- 覆盖持久缓存和页面中旧结果；可提示重新匹配，无需清空全部缓存。禁止添加两首歌的强制接受/拒绝缓存。

| P01 精确截图正例，无 ISRC/专辑/时长 | title_score >= 0.95，artist_score >= 0.95，总分 >= 0.90，无 title_mismatch；可 review，但理由准确 |
| P02 正例去括号、全半角标点、罗马字空格/大小写、交换两侧 | 分差 <= 0.03；标题比较对称，不依赖截图硬编码 |

| P04 正例有可靠身份佐证，无歧义 | 满足现有门槛时 auto_accept；纯转写重复信息不伪造双强证据 |
| N01 sweets parade → magical mode，同艺人 | 缺失/相同/相差 1、2.5、3 秒时长，Single/EP/相同专辑条件下均 no_match、score <= 0.39，无默认候选 |
| N02 其他至少 15 组同歌手不同完整歌名 | 覆盖英文、日文、罗马字与短标题，同专辑/时长不能补成同歌；保留 sweets paper 旧例 |

| U01 实际页面展示上述正例/反例 | 正例高分和准确理由；反例不在主匹配位置展示 magical mode、不自动勾选；换版本入口可用 |

自动测试全部使用模拟凭证、上游与临时缓存，不操作真实歌单。页面行为用独立测试数据验证，不仅查找 HTML 字符串。

验证范围：新 V5 测试、已有 scorer 测试、多语言/日语矩阵、test_name_search_scoring_v3.py、test_one_last_kiss_recall.py、test_stale_review_cache.py、缓存测试；最后全量 pytest 和 git diff --check。旧用例若依赖伪造的 0.60 标题分，先说明旧断言的问题，再改为真实分项与身份行为断言，禁止只放宽门槛。
