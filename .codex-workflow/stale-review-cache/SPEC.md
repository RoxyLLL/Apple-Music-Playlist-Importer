# 旧规则复核缓存导致错误高分：修复规格

## 问题样例

- 来源曲目：`sweets paper` — 花澤香菜（はなざわ かな）
- Apple Music 候选：`magical mode` — 花泽香菜
- 界面截图显示：`72/100 待复核`
- 当前代码现场复算：总分 `0.138`、标题分 `0.083`、艺人分 `1.0`，决策为 `no_match`，不应保留候选。

## 已确认的代码路径

- Web 列表直接显示 `selected_candidate.score * 100`，不是独立的置信度值。
- `MatchCache.get_match()` 目前只对过期版本的 `auto_accept` 重新评分；其他非人工确认缓存（包括 `review`）可能被直接返回。
- 因此旧版本留下的 `review` 记录能把旧分数和错误候选带入当前 UI。人工确认 `user_confirmed` 是明确例外，必须保持。

## 目标

1. 任何由算法产生的缓存结果，只要匹配规则、查询策略、罗马化或例外注册表版本有变化，就不得未经重评继续展示。
2. 对仍有 source track 和候选的缓存，使用当前统一评分器重评完整候选集，并同步更新分数、决策、evidence、候选选择及缓存版本。
3. 若重评结果为 `no_match`，必须清除 `selected_candidate`，防止界面继续显示陈旧的高分候选。
4. 若无法安全重评（缺少源曲目或候选），必须缓存未命中并触发正常搜索/复核路径；不能保留旧的肯定候选或高分。
5. `user_confirmed` 属于用户明确决定，不随算法版本迁移而改写。

## 非目标与约束

- 不针对某首歌或艺人硬编码分数/否定规则。
- 不改界面将“匹配分”伪装成概率；分数仍须来自当前 scorer。
- 不在无证据时把 `review` 改成 `no_match`；要按新规则重算或走安全缓存未命中。
- 不清空整个本地缓存、不删除用户数据、不提交或推送。
